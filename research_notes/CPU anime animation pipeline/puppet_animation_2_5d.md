## 1. Inochi2D (Inochi Creator / Inochi Session / Inox2D / inochi2d-c): format, headless rendering, Python, rigging, licences

### Takeaway
Inochi2D is a real, BSD-2-licensed open alternative to Live2D (mesh-deform puppets driven by parameters), but there is **no official Python binding and no official headless renderer**; rigging is done by hand in the Inochi Creator GUI (it imports PSDs), the runtimes are still labelled prototype/"not ready for production", and the only headless/scripted tooling is two very young third-party 2026 projects whose render-to-PNG step is still "planned"/an open issue. Usable for us only if the owner rigs each character once in the GUI and we build our own offscreen render path (C FFI or WASM) on top.

### Cited Findings
- Inochi2D "is a library for realtime 2D puppet animation and the reference implementation of the Inochi2D Puppet standard"; it "works by deforming 2D meshes created from layered art at runtime based on parameters". Written in D; usable from other languages through a C FFI (`dub build --config=dynamic`), a WebAssembly build (pre-compiled in nightlies and "starting with 0.9, our main releases"), an official Godot GDExtension and an official Unity binding; the Godot binding "should then be able to load in `inx` and `inp` model files". Official SDK bindings list only Unity (no Python). — [Inochi2D README](https://github.com/Inochi2D/inochi2d)
- Licence: BSD 2-Clause, "Copyright (c) 2020-2026, Inochi2D Project / Kitsunebi Games" (library); Inochi Creator, Inochi Session and inochi2d-c are also BSD 2-Clause; Inox2D is BSD 2-Clause. — [inochi2d LICENSE](https://github.com/Inochi2D/inochi2d/blob/main/LICENSE), [inochi-creator LICENSE](https://github.com/Inochi2D/inochi-creator/blob/main/LICENSE), [inox2d README "License"](https://github.com/Inochi2D/inox2d)
- System requirements: x86-64 CPU with SSE4+; "At least 1 GB of RAM for bigger models"; GPU "Depends on renderer backend". — [Inochi2D README](https://github.com/Inochi2D/inochi2d)
- The C SDK (`inochi2d-c`) exposes `inInit(timingFunc)`, `inLoadPuppet("myPuppet.inp")`, `inPuppetGetParameters(...)`, `inParameterGetName`, etc.; using Inochi2D "with your own renderer" requires GPU features: 2 framebuffers, sRGB->linear conversion, premultiplied alpha, vertex buffers, **stencil buffers**, pixel shaders, Porter-Duff blending, and "At least 4096x4096 texture resolution support". — [inochi2d-c README](https://github.com/Inochi2D/inochi2d-c)
- File format: "INP Stands for **In**ochi2D **P**uppet, and is a binary container format to contain Inochi2D model, texture and extra data. INP is subject to change as we get closer to the 1.0 release." Layout: magic bytes `TRNSRTS\0`, big-endian 4-byte JSON payload length, JSON "model and rigging data", `TEX_SECT` texture section, optional `EXT_SECT` vendor data. — [Inochi2D docs, INP spec](https://github.com/Inochi2D/inochi2d-docs/blob/main/docs/source/spec/inp/index.rst)
- A third-party toolkit describes the open format the same way ("a `TRNSRTS` container holding a JSON payload plus textures") and states: "Inochi2D has no official plugin/IPC surface and its editor (Inochi Creator) is a GUI application"; it targets "version v0_8 payloads". Its status table: `new`, `inspect`, `verify`, `textures`, `doctor` implemented; **`from-layers` (layered art -> rigged puppet) "planned"; `render` ("headless render to PNG (via the Creator bridge)") "planned"**. MIT, standard-library Python only. — [yanjingzhaisun/inochi2d-toolkit](https://github.com/yanjingzhaisun/inochi2d-toolkit)
- Another 2026 third-party project, inochi-agent-tools, builds "headless authoring tools" (create puppet, import textures, create parts, create/bind parameters) through a D/C ABI bridge pinned to Inochi2D `v0.8.7`; its CI needs LDC/DUB, Node 22, **Xvfb and xdotool**. Headless preview rendering to PNG is an open issue, and a separate issue reports CLI-authored `.inp` files not rendering correctly in the official WASM runtime (second-hand via search snippet of the issues). — [inochi-agent-tools README](https://github.com/MohamedXIV/inochi-agent-tools), [issue #26](https://github.com/MohamedXIV/inochi-agent-tools/issues/26), [issue #58](https://github.com/MohamedXIV/inochi-agent-tools/issues/58)
- Inox2D (Rust port): "Officially supported experimental Rust port"; "**Currently this library and the specification is in a prototype state**, it is not recommended to use this library in production." Parses INP and INX; OpenGL + WebGL renderers; parameters (mesh deforms, transform offsets) and physics implemented; **animations and mesh groups not implemented** ("newer models which use the MeshGroup feature don't work yet"). — [Inox2D README](https://github.com/Inochi2D/inox2d)
- A Bevy plugin (bevy_inochi2d) loads puppets and can render offscreen via Bevy render targets (second-hand, search snippet; not verified in the repo). — [Huskysis/bevy_inochi2d](https://github.com/Huskysis/bevy_inochi2d)
- Inochi Creator "allows you to rig models"; animation "is achieved by morphing, transforming and in other ways distorting layered 2D textures in real-time"; it depends on a forked `psd-d` (PSD import) and a C++ imgui toolchain to build. — [Inochi Creator README](https://github.com/Inochi2D/inochi-creator)
- Inochi Session (VTubing app): "currently under heavy development and isn't ready for production just yet." — [Inochi Session README](https://github.com/Inochi2D/inochi-session)
- Fork: nijigenerate is an editor for the "nijilive puppet format, which is derived from Inochi2D (v0.8) technology"; "No official stable build provided for time being", nightly/weekly builds only. — [nijigenerate README](https://github.com/nijigenerate/nijigenerate)
- Inochi Creator is listed as the top free/open-source Live2D alternative on AlternativeTo (directory listing, second-hand). — [AlternativeTo: Live2D alternatives](https://alternativeto.net/software/live2d)
- Related (not Inochi2D): `live2d-py` (MIT) wraps the Live2D Cubism Native SDK as a Python C extension, loads Cubism 2.1 and 3.0+ models (`.moc3`, `.model3.json`, `.motion3.json`) and can draw "in any OpenGL-based window" once an OpenGL context exists; the Cubism Core/Framework are **not included** (licence) and must be downloaded from Live2D. — [Arkueid/live2d-py](https://github.com/Arkueid/live2d-py)
- Live2D SDK release licence: individuals and "Small-Scale Enterprises" (latest annual sales under 10 million yen) are exempt from the publication licence and payment, except for "Expandable Applications" such as avatar systems; licence needed only at release. — [Live2D SDK Release License](https://www.live2d.com/en/sdk/license/)

### Inferences
- Rigs are made manually in Inochi Creator (GUI: import PSD, build meshes, define parameters such as head angle/eye open/mouth open, set physics for hair). There is no auto-rigger in the official tools; the third-party `from-layers` auto-rigging is not implemented. So each new character costs hours of GUI rigging by a person — at odds with "no GUI during production", though it is a one-time cost per character.
- Headless rendering on a GPU-less Linux box is plausible but unbuilt: options are (a) build `inochi2d` with `--config=dynamic`, drive it from Python via `ctypes`/`cffi` and supply an OpenGL context from Mesa (llvmpipe via EGL surfaceless/OSMesa or Xvfb); (b) run the WASM/WebGL build in headless Chromium (software GL) and capture frames; (c) Inox2D's OpenGL renderer under Xvfb. All three are engineering projects with no published CPU timings; stencil buffers and 4096-px textures are fine on Mesa llvmpipe in principle (estimate, not tested).
- Because the format is plain JSON + textures, a Python tool could *read* a puppet's meshes and parameter deltas and re-implement deformation on the CPU with NumPy/OpenCV (essentially our DIY warp path in section 2) — this avoids the D toolchain entirely. Estimate only.
- The owner's laptop (RTX 3050 Laptop 4 GB) is the natural place to do the one-time GUI rigging in Inochi Creator (or Live2D Cubism Editor free version); the cloud CPU box would then only render. Live2D models could be rendered from Python via `live2d-py` under Xvfb/Mesa; the owner's channel would fall under the small-scale exemption while revenue stays under 10M yen (verify terms before relying on it).

### Gaps
- The exact definition of `.inx` vs `.inp` was not found in a primary doc. My understanding (unverified) is that `.inx` is Inochi Creator's project/save format and `.inp` the exported puppet; the toolkit and Inox2D treat both as parseable puppet containers.
- No published CPU (software-GL) frame timings for Inochi2D/Inox2D rendering; no official Python binding found (search and repo READMEs).
- Latest release versions/dates of Inochi2D repos could not be retrieved (GitHub API blocked in this session; Atom feeds returned nothing).

## 2. DIY mesh-warp puppetry in Python (piecewise-affine / TPS / MLS warps, layered parts, per-frame compositing) and CPU cost at 1080p

### Takeaway
DIY is fully viable on this CPU: a dense displacement field applied with `cv2.remap` costs **~2-3 ms per 1080x1920 RGBA frame with precomputed maps (~16 ms if the field is rebuilt in NumPy every frame)**, a head-tilt rotation of a head layer ~1-3 ms, and TPS/MLS deformation fields computed on a 1/8-resolution grid then upsampled cost ~65-170 ms per frame in naive NumPy (dominated by the field evaluation, which can be precomputed or cached). Avoid `skimage.transform.PiecewiseAffineTransform` (~5 s per frame) and full-frame NumPy alpha compositing (~0.5 s per frame for 8 layers); composite cropped parts instead. The hard part is not compute but **art preparation** (separated layers with inpainted hidden areas, closed-eye/open-mouth sprites).

### Cited Findings
- Measured on this machine (4 threads, synthetic 1080x1920 RGBA layers; 20 timed frames per op after a warm-up, 2-5 for the slow ops). Other agents were running CPU benchmarks (Blender, Stable Diffusion, upscalers) in parallel, so I timed 4 runs and report the **minimum** (best estimate of uncontended cost) and the range. Contention per run: A 21:24 UTC not logged; B 21:30:51 idle (94%) at start but another job started during the run; C 21:48 other processes used 21.5% of the machine; D 21:52 others 45.8% (from `/proc/stat` minus the benchmark's own rusage, `bench_puppet2d/clean_log.txt`). No fully contention-free run could be obtained in ~25 minutes of retrying. — local logs `bench_puppet2d/runA.txt`, `result.txt`, `run_1.txt`, `run_2.txt`

| Operation (1080x1920 RGBA unless noted) | best (min of 4 runs), ms/frame | range across runs, ms |
|---|---|---|
| `cv2.remap`, displacement field rebuilt each frame in NumPy (breathing + hair-sway field) | 16.0 | 16.0-47.4 |
| `cv2.remap`, precomputed float32 maps | 2.1 | 2.1-15.6 |
| `cv2.remap`, precomputed fixed-point `CV_16SC2` maps | 3.4 | 3.4-43.6 |
| Thin-plate spline (24 control points) evaluated on a 1/8 grid, upsampled, remap | 63.7 | 63.7-251.6 |
| MLS rigid (16 handles) on a 1/8 grid, upsampled, remap | 94.0 | 94.0-168.6 |
| `skimage` `PiecewiseAffineTransform` + `warp` (96 points) | 4,267.8 | 4,267.8-6,688.5 |
| OpenCV per-triangle `warpAffine` + mask (154 triangles) | 155.2 | 155.2-274.8 |
| Head layer 700x700 rotation about the neck pivot (`warpAffine`) | 0.8 | 0.8-3.0 |
| Composite 8 full-frame RGBA layers (NumPy uint16) | 354.1 | 354.1-482.3 |
| Composite 8 full-frame RGBA layers (cv2 float32) | 468.2 | 468.2-615.7 |
| Composite 8 cropped 400x400 RGBA parts onto the 1080x1920 frame | 23.5 | 23.5-32.7 |

- Profiling the TPS path (same machine, run B at ~21:31 UTC, possibly partly contended): TPS kernel evaluation on a 135x240 grid with 24 control points 28.6 ms; upsampling two 240x135 maps to 1080x1920 0.8 ms (linear) / 1.7 ms (cubic); building absolute maps 2.2-2.6 ms; `cv2.remap` of the full RGBA frame 2.9 ms; remap of an 800x900 head/torso crop 1.0 ms. The 64-250 ms total in the timed loop therefore comes mostly from naive NumPy overheads (temporary arrays, float64 linear algebra), not from the warp itself. — local log `bench_puppet2d/result.txt`
- Moving Least Squares deformation (Schaefer, McPhail, Warren, SIGGRAPH 2006) gives closed-form affine, similarity and rigid deformations from handle points; the rigid variant limits local scaling/shear (good for faces/hair). Weights `w_i = 1/|p_i - v|^(2α)` are recomputed per query point. — [Schaefer et al., "Image Deformation Using Moving Least Squares"](https://people.engr.tamu.edu/schaefer/research/mls.pdf)
- `molesq` (PyPI) implements MLS point/image deformation in Python with NumPy arrays of control/deformed points (affine variant per the navis docs; second-hand). — [molesq on PyPI](https://pypi.org/project/molesq)
- scikit-image 0.26 deprecates `PiecewiseAffineTransform.estimate` in favour of `PiecewiseAffineTransform.from_estimate` (observed as a FutureWarning while benchmarking). — local log `bench_puppet2d/result.txt`
- EasyVtuber's no-camera "mouse/audio" input mode loops blinking and breathing on a timer and drives the mouth shape from audio volume — the same procedural recipe a DIY rig would use (it does this on THA output, but the control logic is generic). — [EasyVtuber README](https://github.com/yuyuyzl/EasyVtuber)
- Meta's AnimatedDrawings (MIT code and MIT model weights) rigs a drawn humanoid with a skeleton and retargets BVH motion; it renders to MP4/GIF from Python (`render.start(config.yaml)`) and supports headless rendering with `USE_MESA: True`; auto-annotation needs Docker + TorchServe; designed for human-like figures (body motion, not facial animation). — [facebookresearch/AnimatedDrawings](https://github.com/facebookresearch/AnimatedDrawings)

### Inferences
- A practical DIY rig for dialogue shots: layers = back hair, body, neck, head (face base), eyes (open / half / closed sprites), brows, mouth (closed / mid / open, optionally A-I-U-E-O), front hair, accessories. Per frame: (1) breathing = small vertical scale of the torso about the waist via one precomputed analytic remap (~3-20 ms); (2) head tilt/nod = `warpAffine` of the head group about the neck pivot (~2 ms); (3) "head turn" = small horizontal MLS/TPS shift of face features relative to the face outline plus parallax between hair-back/face/hair-front layers (field precomputed for ~5-9 turn poses and blended); (4) hair sway = remap whose amplitude grows with distance from the scalp, driven by a damped spring for follow-through; (5) blinks = sprite swap on a random 2-6 s timer with 1-2 half-closed frames; (6) mouth flaps = sprite chosen from the TTS audio RMS envelope (or Whisper word timings for vowels). Compositing cropped parts keeps a frame at roughly 25-60 ms of CPU, i.e. **a 45 s Short at 30 fps (1,350 frames) renders in ~1-2 minutes of CPU per character shot** (estimate from the measured per-op costs; not measured end-to-end).
- Precompute deformation fields per pose key (e.g., head-turn -1..+1 in 9 steps) once and interpolate between them per frame; this removes the ~65-170 ms TPS/MLS evaluation from the per-frame loop.
- This approach keeps the original illustration's quality at full 1080p resolution, unlike the neural methods in section 3 (512x512 output).
- On the owner's laptop the same OpenCV code runs on the laptop CPU (i7 11th gen) at similar or better speed; a GPU is not needed for this path.

### Gaps
- No public, sourced CPU benchmarks for 2.5D DIY puppet pipelines were found; all numbers above are my own synthetic micro-benchmarks, not an end-to-end render with real art.
- No ready-made, maintained open-source "Live2D-like from PSD in Python" library was found; the DIY approach must be built.

## 3. Neural single-image anime animation (THA3/THA4, EasyVtuber, LivePortrait, SadTalker, AniPortrait, LiteAvatar): inputs, outputs, speed (CPU and RTX 3050 Laptop 4 GB), quality, licences

### Takeaway
**THA3 is the only mature open model built for anime** that does exactly breathing, blinks, mouth vowels, eyebrow moods, iris, head/neck/body rotation from one image, and its weights are **CC BY 4.0 (commercial use allowed with attribution)**. But it outputs 512x512 only, requires a strict input layout, is GPU-oriented (36-65 ms/frame on 2017-2020 GPUs; no CPU numbers published), and the newer THA4 weights are **CC BY-NC 4.0** (not for a monetised channel). LivePortrait (MIT code) and SadTalker (Apache-2.0) are human-face models whose pipelines depend on human face detectors (LivePortrait's default InsightFace models are non-commercial); there is no reliable evidence they handle anime faces well, and both are slow on CPU. AniPortrait is a Stable-Diffusion video model: not realistic on this CPU. On the owner's RTX 3050 Laptop (4 GB), THA3 should fit and run at roughly 6-40 fps depending on variant and runtime (closest measured proxy: GTX 1660 Super 12-38 fps with TensorRT) — fast enough for offline rendering of Shorts at 512x512; LivePortrait and SadTalker are borderline on 4 GB; See-through/Qwen-Image-Layered do not fit.

### Cited Findings
**THA3 (Talking Head(?) Anime from a Single Image 3)**
- Inputs: a single image; "It should be of resolution 512 x 512" (other sizes are resized and output at 512x512); "It must have an alpha channel"; one humanoid character, "standing upright and facing forward"; hands "below and far from the head"; head "roughly contained in the 128 x 128 box in the middle of the top half of the image"; background alpha must be 0. — [THA3 demo README](https://github.com/pkhungurn/talking-head-anime-3-demo)
- Controls: "facial expression, head rotation, body rotation, and chest expansion due to breathing". THA3 takes "an image of an anime character's upper body and a 45-dimensional pose vector". The pose parameter names in the code are: eyebrow_troubled/angry/lowered/raised/happy/serious, eye_wink, eye_happy_wink, eye_surprised, eye_relaxed, eye_unimpressed, eye_raised_lower_eyelid, iris_small, mouth_aaa/iii/uuu/eee/ooo, mouth_delta, mouth_lowered_corner, mouth_raised_corner, mouth_smirk, iris_rotation_x/y, head_x, head_y, neck_z, body_y, body_z, breathing (most face ones have left/right halves, giving 45 dims). — [THA3 README](https://github.com/pkhungurn/talking-head-anime-3-demo), [THA4 paper](https://arxiv.org/abs/2311.17409), `tha3/poser/modes/pose_parameters.py` in the [THA3 repo](https://github.com/pkhungurn/talking-head-anime-3-demo/blob/master/tha3/poser/modes/pose_parameters.py)
- Hardware stated: "Both programs require a recent and powerful Nvidia GPU"; the demo apps are wxPython GUIs / a Jupyter notebook (no CLI renderer, but the poser is a plain PyTorch API: `load_poser(variant, device)` then `poser.pose(image, pose)`). — [THA3 README](https://github.com/pkhungurn/talking-head-anime-3-demo)
- Four variants: standard_float (default; "largest, slowest, and most accurate"), separable_float, standard_half, separable_half. Model download zip is 834,700,485 bytes; per-variant file sizes from the zip listing: standard_float ≈ 543 MB, standard_half ≈ 271 MB, separable_float ≈ 58 MB, separable_half ≈ 29 MB (verified by download). — [THA3 README](https://github.com/pkhungurn/talking-head-anime-3-demo), [Dropbox link in README](https://www.dropbox.com/s/y7b8jl4n2euv8xe/talking-head-anime-3-models.zip?dl=0)
- Licences: code MIT; "The model files are distributed with the Creative Commons Attribution 4.0 International License, which means that you can use them for commercial purposes. However, if you distribute them, you must, among other things, say that I am the creator." Sample images are CC BY-NC (Lambda) or under the Crypko guideline — don't use them in videos. Author notes Google "might claim the rights to the intellectual property of this invention". — [THA3 README](https://github.com/pkhungurn/talking-head-anime-3-demo), [data/images/README.md](https://github.com/pkhungurn/talking-head-anime-3-demo/blob/master/data/images/README.md)
- Speed (GPU only, from the THA4 paper, averages of 1,000 frames): THA3 (128 MB+517 MB system) 35.9 ms on RTX A6000, 41.4 ms on Titan RTX, **64.6 ms on GTX 1080 Ti**; "THA3 can in the best case achieve around 30 FPS on a machine with very powerful GPUs". — [THA4 paper (HTML)](https://arxiv.org/html/2311.17409v2)
- A PyPI wrapper `tha3` (0.1.9, "MIT; CC-BY-4.0") packages the demo with the `separable_float` model and exposes the GUIs (`tha3`, `tha3i`). — [tha3 on PyPI](https://pypi.org/project/tha3/)
- No CPU benchmark for THA3 was found in any source searched (README, PyPI, web search). — [search: tha3 PyPI page](https://pypi.org/project/tha3/)

**THA4**
- "Improved model" is "too slow to run in real-time"; real-time use requires distilling a per-character "student model" (< 2 MB) from a 512x512 RGBA image **plus a hand-made black-and-white mask of the eyes and mouth**; training "was about 30 hours on a computer with an Nvidia RTX A6000 GPU". Requires a recent Nvidia GPU (developed on RTX A6000, "anything after the GeForce RTX 2080 should be fine"). — [THA4 demo README](https://github.com/pkhungurn/talking-head-anime-4-demo)
- Licences: code MIT (copyright pixiv Inc.); "**The THA4 models and the images under the `data/images` directory are released under the Creative Commons Attribution-NonCommercial 4.0 International**". — [THA4 demo README](https://github.com/pkhungurn/talking-head-anime-4-demo)
- Speed (GPU): teacher 125.8 / 116.8 / 159.6 ms per frame and student 12.5 / 15.1 / 22.1 ms per frame on RTX A6000 / Titan RTX / GTX 1080 Ti; student is 1.8 MB vs 627 MB; student PSNR 34.5-36.2 dB vs teacher. — [THA4 paper (HTML)](https://arxiv.org/html/2311.17409v2)
- Student models are converted to TensorFlow.js for the browser demos (conversion code not released). — [THA4 demo README](https://github.com/pkhungurn/talking-head-anime-4-demo), [THA4 project page](https://pkhungurn.github.io/talking-head-anime-4/)

**EasyVtuber (THA3/THA4 wrapper)**
- MIT; fork of GunwooHan/EasyVtuber; Windows 10/11 tested; uses ONNX conversions of THA (from ezvtuber-rt) with TensorRT (Nvidia) or DirectML (AMD/Intel), RIFE frame interpolation, waifu2x/Real-ESRGAN super-resolution, THA v4 support. — [EasyVtuber README](https://github.com/yuyuyzl/EasyVtuber)
- Measured by the EasyVtuber authors (Windows, i5-10400F, TensorRT, 60 fps cap): **desktop RTX 3060 12 GB**: separable_half 63 fps, separable_full 59 fps, standard_half 63 fps, standard_full 31 fps; with x2-x4 RIFE interpolation 64 fps at 30-50% GPU; GTX 1660 Super 6 GB: 12-38 fps; RX 580 8 GB: 12-15 fps (22-33 fps with interpolation). No CPU-only numbers. — [EasyVtuber PerformanceTest.md](https://github.com/yuyuyzl/EasyVtuber/blob/main/PerformanceTest.md)
- ezvtuber-rt (ONNX/TensorRT THA3 + RIFE + waifu2x + Real-ESRGAN, "Removed dependency from PyTorch"): minimum hardware "AMD RX580 and up, Intel Arc a750 and up, Nvidia GTX1650 and up" (reaching 25 fps after interpolation); "THA3 weights are not good for INT8 quantization in PTQ method". — [zpeng11/ezvtuber-rt](https://github.com/zpeng11/ezvtuber-rt)

**LivePortrait**
- Code and weights MIT (Kuaishou). Speed table (RTX 4090, PyTorch + torch.compile, one frame): appearance extractor 0.82 ms, motion extractor 0.84 ms, SPADE generator 7.59 ms, warping module 5.21 ms, stitching/retargeting 0.31 ms; parameters 0.84 M + 28.12 M + 55.37 M + 45.53 M + 0.23 M (~130 M, ~500 MB of weights). — [LivePortrait LICENSE](https://github.com/KwaiVGI/LivePortrait/blob/main/LICENSE), [speed.md](https://github.com/KwaiVGI/LivePortrait/blob/main/assets/docs/speed.md)

### Inferences
- **THA3 on this CPU (estimate, not measured):** the GTX 1080 Ti does ~11 FP32 TFLOPS; this 4-vCPU Xeon peaks at a few hundred GFLOPS FP32 (more with AMX-BF16 if PyTorch/oneDNN uses it). Treat as an order-of-magnitude guess until timed (the clone + separable_float weights are ready in the scratchpad).

THA3 also redraws the whole character, so line quality is below the source art; DIY warping (section 2) keeps the original pixels.
- THA3 commercial use: weights CC BY 4.0 → allowed on a monetised channel with attribution (credit Pramook Khungurn in the description); the author's note about Google possibly claiming IP rights is a residual risk. THA4 (CC BY-NC) and LivePortrait with default InsightFace (non-commercial) are not safe for a monetised channel; LivePortrait with MediaPipe detection is MIT/Apache.

Not recommended for anime without testing.
- **RTX 3050 Laptop, 4 GB (owner's laptop) — estimates unless stated:**

Speed: the measured GTX 1660 Super (≈5 TFLOPS, 6 GB) numbers with TensorRT are the best proxy — separable_half 38 fps, separable_full 28 fps, standard_half 21 fps, standard_full 12 fps; plain PyTorch fp32 scaled from 64.6 ms on a GTX 1080 Ti suggests ~100-170 ms per frame for standard_float on the 3050 Laptop (~6-10 fps). For offline rendering that is ~2-3 minutes per 45 s shot at 24 fps — perfectly usable. EasyVtuber itself is Windows-only/GUI; for scripted rendering call the THA3 PyTorch poser directly.
  - *THA4:* student inference (22 ms on a GTX 1080 Ti) would be real-time, and the teacher (627 MB) would fit for slow offline posing, but the THA4 weights are CC BY-NC (unusable on a monetised channel) and distilling a student took ~30 h on a 48 GB RTX A6000 — expect several times longer on a 4 GB laptop card, if it fits at all.
  - *LivePortrait:* third-party guides say 8 GB minimum; its ~130 M parameters (~500 MB fp32, half precision on by default via `flag_use_half_precision`) suggest single-image inference at the 256 px crop may still fit in 4 GB, but this is unverified; speed perhaps 100-300 ms/frame (scaled from 12.8 ms on an RTX 4090). Default InsightFace detector is non-commercial; use MediaPipe.
  - *SadTalker:* a tutorial calls 4 GB the recommended minimum and a forum reply suggests the 256 px model for low VRAM — so 4 GB is the edge; anime faces likely fail its human-face pipeline anyway.
  - *AniPortrait:* SD1.5 + reference UNet + motion module video diffusion; not realistic on 4 GB.

## 4. Automatic layer separation of anime illustrations and anime face/landmark detection (CPU cost, accuracy)

### Takeaway
Background removal and face landmarks are cheap and permissively licensed (skytnt anime-segmentation / rembg `isnet-anime`, Apache-2.0, 176 MB ONNX; hysts anime-face-detector, MIT, 28 landmarks, now without OpenMMLab). Full **part-level layer decomposition** now exists as research code — **See-through (SIGGRAPH 2026, Apache-2.0 code)** splits one anime illustration into up to 23 inpainted layers exported as PSD — but it needs ~14 GB of model downloads and a 8-16 GB VRAM GPU, so it does not fit this CPU box (disk alone rules it out) and does not fit the owner's 4 GB RTX 3050 Laptop either. Qwen-Image-Layered (Apache-2.0) is 41 GB in BF16 (7.4-13 GB GGUF quantisations). Bunraku (Jul 2026) goes further (layers + meshes + keyposes, i.e. auto-rigging) but no code release was found.

### Cited Findings
- skytnt/anime-segmentation: "Segmentation for anime character"; supported nets ISNet, U2Net, MODNet, InSPyReNet; export to ONNX at `--img-size 1024`; trained on AniSeg + character_bg_seg_data, cleaned with DeepDanbooru and manually; Apache-2.0. HF model repo files: `isnetis.onnx` 176,069,933 bytes, `isnetis.ckpt` 204 MB, `model.safetensors` 204 MB (Apache-2.0). — [skytnt/anime-segmentation](https://github.com/SkyTNT/anime-segmentation), [HF skytnt/anime-seg](https://huggingface.co/skytnt/anime-seg)
- rembg bundles it as `isnet-anime` ("A high-accuracy segmentation for anime character", source SkyTNT/anime-segmentation); rembg itself is MIT. — [danielgatis/rembg README](https://github.com/danielgatis/rembg), [rembg LICENSE](https://github.com/danielgatis/rembg/blob/main/LICENSE.txt)
- hysts/anime-face-detector: "anime face detector with facial landmark estimation, implemented in plain PyTorch"; Faster R-CNN and YOLOv3 face detectors + HRNetV2 landmark model, **28 landmark points**; "detects near-frontal anime faces"; "since v0.1.0 this package runs them without any OpenMMLab runtime dependency"; `pip install anime-face-detector`; MIT (vendored mmpose/mmdet/mmcv code Apache-2.0). HRNetV2 weights: 9,678,034 F32 parameters (HF repo created 2026-07-05). — [hysts/anime-face-detector](https://github.com/hysts/anime-face-detector), [HF hysts/anime-face-detector-hrnetv2](https://huggingface.co/hysts/anime-face-detector-hrnetv2)
- See-through (Lin et al., arXiv 2602.03749, Feb 2026; ACM SIGGRAPH 2026 Conference Papers): "decomposes a single image into fully inpainted, semantically distinct layers with inferred drawing orders — up to **23 layers** including hair, face, eyes, clothing, accessories"; main script `inference/scripts/inference_psd.py --save_to_psd`; models: LayerDiff 3D (SDXL-based transparent layer generation), Marigold depth fine-tuned for anime, SAM body parsing; "requires approximately 12-16 GB of VRAM at 1280 resolution" (bf16); group offload ~10 GB (~1.5x slower); **NF4 quantised pipeline ~8 GB peak VRAM at 1280** (PSNR ~30 dB, SSIM ~0.96 vs bf16), "can be further reduced by lowering the resolution"; block-swap pipeline ~8 GB; trained on 8x H200; HF ZeroGPU Space allows "1-2 PSD extractions per day (approximately 2-3 mins each, at 1280 resolution)"; installs CUDA 12.8 PyTorch wheels; code Apache-2.0. — [shitagaki-lab/see-through](https://github.com/shitagaki-lab/see-through), [arXiv 2602.03749](https://arxiv.org/abs/2602.03749)
- See-through authors on limits: "Is this Image-to-Live2D? We don't think so — at least, not yet": Live2D needs finer artist-designed layer splits and **rigging ("deformation mesh, physics parameters, and motion curves") "is not covered in this project"**; positioned as a "starting point" removing "manual segmentation and occluded region inpainting". — [See-through README](https://github.com/shitagaki-lab/see-through)
- Hands-on test (second-hand, RunPod RTX PRO 6000 96 GB): model downloads LayerDiff 3D 9.5 GB + Marigold 3.1 GB + SAM body parsing 1.3 GB ≈ 14 GB (~15 GB with repo); inference **2 min 5 s** per image; output PSD 7.9 MB with 23 parts (front hair, back hair, face, eyebrow, eyelash, eyewhite, irides, mouth, nose, ears, headwear, neckwear, topwear, handwear, bottomwear, legwear, footwear, neck, head, ...); stacked reconstruction "nearly identical to the original"; failures: side ponytail merged into back hair, footwear PNG missing from the PSD; inpainting "reasonably well"; face split into 7 parts vs 3 for Qwen-Image-Layered; licence of the three model weights not stated in that article. — [lilting.ch hands-on](https://lilting.ch/en/articles/see-through-anime-layer-decomposition)
- Bunraku (arXiv 2607.27348, 29 Jul 2026): from a single illustration generates ordered RGBA layers with hidden-region completion, a deformation mesh per layer and parameter-driven keypose vertex offsets ("Live2D" asset end-to-end); per-vertex direction cosine 0.768 (median 0.828) on 50 held-out characters; introduces Live2D-Bench and an 8,884-model corpus; code release not stated on arXiv; paper licence CC BY-NC-SA 4.0. — [arXiv 2607.27348](https://arxiv.org/abs/2607.27348)
- Qwen-Image-Layered: "decomposing an image into multiple RGBA layers"; variable number of layers (e.g. 3 or 8); recommended resolution bucket 640; exports pptx/zip/psd; weights released 2025-12-19; Apache-2.0. Full HF repo ~57.7 GB; Unsloth GGUF (Apache-2.0): BF16 40.87 GB, Q8_0 21.76 GB, Q4_K_M 13.24 GB, Q3_K_S 9.22 GB, Q2_K 7.39 GB; Unsloth advises total RAM+VRAM "slightly larger than the GGUF size". Second-hand: 75 s/image at 640 and 240 s at 1024 on a large GPU. — [QwenLM/Qwen-Image-Layered](https://github.com/QwenLM/Qwen-Image-Layered), [HF unsloth/Qwen-Image-Layered-GGUF](https://huggingface.co/unsloth/Qwen-Image-Layered-GGUF), [Unsloth ComfyUI guide](https://unsloth.ai/docs/new/comfyui), [lilting.ch](https://lilting.ch/en/articles/see-through-anime-layer-decomposition)
- LayerDiffuse ("Transparent Image Layer Diffusion using Latent Transparency", Apache-2.0) is a generator of transparent layers (Forge / Diffusers CLI), not a decomposer; See-through builds on it. — [lllyasviel/LayerDiffuse](https://github.com/lllyasviel/LayerDiffuse), [See-through acknowledgements](https://github.com/shitagaki-lab/see-through)

### Inferences
- On this CPU box: `isnet-anime` (176 MB ONNX, onnxruntime is already installed system-wide) and the 28-point anime landmark model are the realistic automatic steps — run once per character image, so even a few seconds each is irrelevant (CPU time estimated at ~1-5 s per image at 1024 px; not measured). Landmarks give eye/mouth/brow boxes for cutting sprite regions and for placing warp handles.
- See-through on CPU is not practical here: ~14 GB of weights vs ~5-6 GB free disk and 15 GB RAM, and SDXL-class diffusion on 4 cores would take a very long time per image (estimate: tens of minutes to hours). Options: the HF ZeroGPU Space (1-2 images/day, ~2-3 min each; scriptable via `gradio_client` with an HF login — inference, not tested), the ModelScope demo, a rented GPU (~$0.17 per image in the hands-on), or the owner's laptop.
- **RTX 3050 Laptop, 4 GB:** See-through's lightest documented pipelines (NF4 or block-swap) still peak at ~8 GB VRAM at 1280 px; lowering resolution with group offload reduces this further, but 4 GB is very unlikely to be enough (estimate) — use the free HF/ModelScope demos or a rented GPU for the one-time decomposition per character. Qwen-Image-Layered's smallest GGUF (Q2_K, 7.4 GB) is almost twice the card's VRAM and would rely on system-RAM offload (slow, quality loss at 2-bit). Background removal (176 MB ONNX) and the anime landmark model (~10 M parameters) are trivial on the 4 GB card or on either CPU.
- Even with perfect decomposition, rigging is still manual (See-through authors say so); for our purposes the useful outputs are the separated eyes/eyewhite/irides/mouth/front-hair/back-hair layers, which map directly onto the DIY rig in section 2.

### Gaps
- No CPU timing for anime-segmentation, anime-face-detector or See-through was found; I did not run them (downloaded-code/model execution was blocked for THA3, so I did not attempt these).
- Landmark accuracy figures for hysts/anime-face-detector were not found in the README.
- The licence of See-through's released model weights is not stated in the README excerpt I read (code is Apache-2.0); LayerDiff 3D is SDXL-based, so the SDXL licence terms may also apply — check before commercial use.

## 5. Making closed-eye and open-mouth variants by inpainting / img2img (on CPU)

### Takeaway
Generating a few expression sprites (eyes half/closed, mouth mid/open) is a one-time cost per character, so CPU diffusion is acceptable: FastSD CPU (MIT) runs SD-Turbo/SDXS-class img2img in ~1 s per 512 px image on a desktop CPU and now does instruction image editing with FLUX.2-klein-4B (Apache-2.0) in OpenVINO int4 (4.58 GB, ~8 GB RAM). Reported experience: "eyes closed" edits work with simple prompts, mouth-open edits are less reliable at small sizes, and unmasked img2img drifts face style/colour — so mask only the eye/mouth region and paste the result back over the original. No anime-specific quality study was found.

### Cited Findings
- Flux.1 schnell experiment (img2img, inpaint, "donut mask" inpaint, MediaPipe guide images): "closing eyes or eyes closed" prompts "work fine", stubborn cases need "closing eyes tightly, shut eyes"; mouth-open guide images "will not work with 512 medium or more small size" (tested 512/1024/1536, 1536 strongest); in img2img the face and style/colour changed; areas outside the guide stayed essentially unchanged even without a mask. Tested on photo-style portraits, no timings. — [Akjava, HF blog](https://huggingface.co/blog/Akjava/result-guide-image-eyes-mouth)
- The same author's Space builds talking-head WebP animations from normal, eyes-closed and mouth-open images (second-hand via search snippet). — [Akjava Space](https://huggingface.co/spaces/Akjava/CreateConsistentCharacterFacialAnimationWithImg2Img)
- General consistency tips (second-hand, manga-focused guide): reuse the same reference/seed, stay on one model, denoising 0.3-0.5 for subtle changes; anime eyes are hard to inpaint singly because one eye "has to match its pair exactly in shape, size, color, and shading". — [Anifusion character consistency tips](https://anifusion.ai/articles/character-consistency-tips/)
- FastSD CPU (MIT): "Using OpenVINO (SDXS-512-0.9), it took **0.82 seconds** ... to create a single 512x512 image on a Core i7-12700"; OpenVINO image-to-image support; img2img for Turbo models; basic ControlNet v1.1 in LCM-LoRA mode; image editing via FLUX.2-klein-4B (OpenVINO int4, added 2026-06-21) and FLUX.3 Image Klein (added 2026-10-25, "FLUX Kommunity License" weights); minimum RAM: LCM 2 GB, LCM-LoRA 4 GB, OpenVINO (Flux2) 8 GB; iGPU support via `DEVICE=GPU`. — [rupeshs/fastsdcpu](https://github.com/rupeshs/fastsdcpu)
- FLUX.2 [klein] 4B: "Fully open under Apache 2.0", unified generation + editing, multi-reference editing, "runs on consumer hardware, with as little as 13GB VRAM". OpenVINO int4 conversion `rupeshs/flux2-klein-4b-int4-ov` is Apache-2.0, 4.58 GB total. — [HF black-forest-labs/FLUX.2-klein-4B](https://huggingface.co/black-forest-labs/FLUX.2-klein-4B), [HF rupeshs/flux2-klein-4b-int4-ov](https://huggingface.co/rupeshs/flux2-klein-4b-int4-ov)
- THA3 can itself produce closed-eye/wink and A-I-U-E-O mouth frames from one image (pose parameters `eye_wink`, `mouth_aaa` ... `mouth_ooo`), which could be used only to *author sprites* (then composited at full resolution) rather than to render every frame. — [THA3 pose_parameters.py](https://github.com/pkhungurn/talking-head-anime-3-demo/blob/master/tha3/poser/modes/pose_parameters.py)

### Inferences
- Recommended sprite workflow (estimate of effort, not tested): detect landmarks → crop eye and mouth regions with margin → inpaint/edit only those crops (FLUX.2-klein edit "close her eyes"/"open her mouth slightly, same style", or SD-Turbo inpaint at low denoise) → feather-paste back into the original so nothing else changes → hand-pick the best of N seeds. On 4 CPU cores a FLUX.2-klein 4-step int4 edit at 512-768 px likely takes on the order of a minute (estimate; FastSD publishes no klein timings), fine for ~4-8 sprites per character. Disk: the 4.58 GB model fits only after freeing space (~5-6 GB free now).
- For a hand-drawn/2D-channel look, closed eyes can also be drawn procedurally (a curved lash line in the eye's colour over the inpainted skin) once the eye region is known — no diffusion needed.
- On the RTX 3050 Laptop (4 GB), SD1.5-class inpainting in fp16 is the realistic GPU option (SDXL-class models generally need CPU offload at 4 GB) — common community experience, not verified here; FLUX.2-klein's stated 13 GB VRAM rules it out on the GPU, but FastSD CPU's OpenVINO int4 path runs on the laptop's Intel i7 CPU (and supports Intel iGPUs via `DEVICE=GPU`), given ≥8 GB free system RAM.

### Gaps
- No source measured anime-specific consistency for eye/mouth variants (identity drift, line-weight match).
- No published CPU timing for FLUX.2-klein editing in FastSD CPU; I did not run it.

## 6. What small creators actually use for anime-style motion comics / talking anime videos on a budget

### Takeaway
Second-hand evidence (Reddit not reachable; search returned directories, vendor blogs and tutorials) points to cheap sprite-swap methods — PNGtuber-style 2-4 images (eyes open/closed x mouth open/closed) switched by voice volume, CapCut-style blink edits, layered parallax "motion comic" pans — plus paid puppet tools (Live2D, Adobe Character Animator, Cartoon Animator) and, increasingly, hosted AI image-to-video/lip-sync services. Live2D-quality rigs are usually commissioned and expensive; Inochi Creator is the main free option.

### Cited Findings
- PNGtuber standard: veadotube lets you "add 4 images" for basic, speaking, blinking and speaking-while-blinking states and switches automatically when you speak; guides recommend 2-4 images minimum, optionally 3 mouth shapes for more natural lip sync and half-closed eye frames for smoother blinks (second-hand tutorials). — [TechTactician veadotube tutorial](https://techtactician.com/veadotube-png-vtuber-avatar-software-tutorial), [Clip Studio PNGtuber tutorial](https://tips.clip-studio.com/en-us/articles/10101)
- Motion comic = "digital, voiced comics with looping animations of some elements"; mouth flaps = "the open/close/pause sequence of mouth movements corresponding to an animated character's dialogue", often not synced to the words (definitions). — [TV Tropes: Mouth Flaps](https://tvtropes.org/pmwiki/pmwiki.php/Main/MouthFlaps), [TV Tropes: Animation Tropes](https://tvtropes.org/pmwiki/pmwiki.php/Main/AnimationTropes)
- Beginner tutorials show making a still anime/manga character blink in CapCut. — [YouTube: "How To Animate Manga In Capcut: Blinking Eye"](https://www.youtube.com/watch?v=pt_uPsZ6u-g)
- A budget-animation blog: simple character + voiceover + icons/transitions is the most common cheap YouTube style; a rigged VTuber-style model can be reused across emotions but commissioning one is expensive; Adobe Character Animator suits talking-head content with auto lip-sync (vendor blog, second-hand). — [air.io affordable animation workflows](https://air.io/en/youtube-hacks/affordable-animation-workflows-for-creators-without-pixar-budgets)
- Paid alternatives listed by software directories: Cartoon Animator (CTA), Plotagon (~$27/year), etc. — [Slashdot: Live2D alternatives](https://slashdot.org/software/p/Live2D/alternatives)
- A creator without Photoshop exported parts from Inkscape and rebuilt them in Krita for Live2D — the PSD requirement is a workflow hurdle for free-tool users. — [itch.io "Generi-chan" asset page](https://eddiejr-digiarts.itch.io/generi-chan)
- See-through's authors describe manual segmentation and occluded-region inpainting as "the most tedious part" of Live2D artists' workflow. — [See-through README](https://github.com/shitagaki-lab/see-through)
- EasyVtuber's pitch (Chinese tagline: spend the money you'd pay for a Live2D "skin" on any graphics card instead) shows THA-based single-image animation is used by hobby VTubers as a Live2D substitute. — [EasyVtuber README](https://github.com/yuyuyzl/EasyVtuber)

### Inferences
- For a Shorts channel, the proven low-budget look is: still illustration + slow push-in/parallax + blink + 3-state mouth flaps synced to the TTS envelope + occasional head tilt/breathing loops — exactly what the DIY rig in section 2 produces cheaply and headlessly, with no licence exposure beyond the art itself.
- Neural single-image methods (THA3) are a "nice-to-have" for head turns and expressive eyebrows on the owner's laptop GPU, not a requirement.
